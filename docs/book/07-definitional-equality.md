## 7.1 The idea

Chapter 3 put values inside types. This chapter pays the bill.

**The idea in one line.** Two descriptions may name one thing, and a checker
has to decide when they do.

A picture. "Three" and "two plus one" are two descriptions. They name one
number. A person settles that in a moment, by doing the arithmetic. **A type
checker has to do the arithmetic too**, because chapter 3 let a type hold a
number.

So here is the question of the chapter. A rule asks for a `Vector α 3`. You
have a `Vector α (2 + 1)`. Are they the same type?

They must be, else nothing works. So a checker needs a notion of "the same by
computation", and that notion has a name,
[definitional equality](../GLOSSARY.md#definitional-equality), written `≡`.

**In your language.** You have already watched a compiler do this and run out
of patience. `tsc` reduces a conditional type, and `tsc` gives up at a budget.
Section 7.4 is that budget inside a kernel, and the TypeScript section at the
end shows the error with the real message.

Now the thing to see clearly. There are **two** notions of sameness in this
book, and they are not the same notion.

| | sameness by computation | sameness by proof |
|---|---|---|
| who settles it | the checker, by running your code | you, by writing a term |
| written | `≡` | `=` |
| costs | time | a proof |

Section 7.3 is that table in full. Section 7.4 is the place where the two come
apart, and it is the one page of Part I that pays for itself a hundred times.

The consequence for the design. **A proof checker holds an evaluator.** No
other kind of checker needs one. The rest of this chapter is the equations that
evaluator obeys, and the order in which it tries them.

## 7.2 The notation, and the seven ways two terms can be the same

The conversion rule from section 5.3 is where `≡` is used:

```
   Γ ⊢ e : A      A ≡ B      Γ ⊢ B : Sort u
   ----------------------------------------
                Γ ⊢ e : B
```

Read it once more now that you know what `≡` is for: **a term keeps its type
under computation**.

`≡` is generated by a short list of equations. Five of them carry Greek
letters, because the literature named them before the computers arrived.

| Name | Equation | In words |
|---|---|---|
| **[β beta](../GLOSSARY.md#beta)** | `(fun x => b) a ≡ b[x := a]` | call a function |
| **[δ delta](../GLOSSARY.md#delta)** | `c ≡ v`, when the environment holds `def c := v` | unfold a definition |
| **[ζ zeta](../GLOSSARY.md#zeta)** | `let x := v; b ≡ b[x := v]` | unfold a local definition |
| **[ι iota](../GLOSSARY.md#iota)** | `Nat.rec z s (Nat.succ n) ≡ s n (Nat.rec z s n)` | run a recursor |
| **[η eta](../GLOSSARY.md#eta)** | `fun x => f x ≡ f` | a wrapper is the thing itself |

And Lean adds two more that are not reductions at all.

| Name | Rule |
|---|---|
| **[proof irrelevance](../GLOSSARY.md#proof-irrelevance)** | if `P : Prop` and `h₁ : P` and `h₂ : P`, then `h₁ ≡ h₂` |
| **a projection** | `S.mk a b` has first field `a`, so reading it is one step |

**In Lean.** Watch two of them run. Both lines below are accepted, and neither
needs a tactic:

```lean
example (f : Nat → Nat) : (fun x => f x) = f := rfl      -- η
example (p : Prop) (h1 h2 : p) : h1 = h2 := rfl          -- proof irrelevance
```

## 7.3 Two equalities, and this is the confusing part

This table is the one to keep.

| | `a ≡ b` | `a = b` |
|---|---|---|
| what it is | a [judgment](../GLOSSARY.md#judgment) of the checker | a [proposition](../GLOSSARY.md#proposition), the inductive type `Eq` |
| who decides | the kernel, by computation | you, with a proof |
| can you state it in Lean | no. It is not a term. | yes. It is a type. |
| what it costs | time | a proof term |

`rfl` is the bridge between the two columns. **`rfl : a = b` type checks exactly
when `a ≡ b`.** So every time you write `rfl`, you are asking the kernel to
compute.

## 7.4 Computation has a direction

Here is the example that teaches this chapter better than any rule. Both lines
look alike. One is accepted and one is refused.

```lean
example (n : Nat) : n + 0 = n := rfl      -- accepted
example (n : Nat) : 0 + n = n := rfl      -- REFUSED
```

The error is real, and this is what Lean prints:

```text
error: Type mismatch
  rfl
has type
  ?m.9 = ?m.9
but is expected to have type
  0 + n = n
```

Why the difference? `Nat.add` recurses on its **second** argument. So:

- `n + 0` has a constructor in the second slot, `Nat.zero`, so ι fires, and the
  term reduces to `n`. The two sides become the same term.
- `0 + n` has a **variable** in the second slot. No ι rule fires. The term is
  **[stuck](../GLOSSARY.md#stuck)**, and `0 + n` and `n` are different terms.

Both statements are true. Only one is true **by computation**. The other needs
a proof, and the proof is induction, which chapter 6 told you is a recursion:

```lean
example (n : Nat) : 0 + n = n := by
  induction n with
  | zero => rfl
  | succ k ih => rw [Nat.add_succ, ih]
```

If you remember one thing from Part I, remember this pair of lines. Half of the
surprises in Lean are this pair wearing a different hat.

**And you have met "stuck" already.** A TypeScript conditional type over a bare
type parameter does not reduce either:

```ts
type IsString<T> = T extends string ? true : false   // waits while T is open
```

`tsc` does not report an error there. It waits until the scrutinee is a real
type. **A stuck term is not an error. It is an answer that is waiting for an
argument.** That sentence is true of both compilers.

## 7.5 Weak head normal form

A checker almost never needs a full normal form. It needs to know **what shape
the term has at the top**, so it can pick a rule. The tool for that is
[`whnf`](../GLOSSARY.md#whnf), which is short for weak head normal form.

```
whnf(e)  =  reduce e until the outermost shape cannot change
```

The two words in the name are the two limits.

- **Weak** means it does not go inside a binder. It leaves the body of a
  `fun` alone.
- **Head** means it only reduces the outermost application, and leaves the
  arguments alone.

An example. Our checker reduces this and stops:

```
(fun x => (fun y => y) x)   ⟶   itself
```

There is a redex inside the body, and `whnf` leaves it there, because nobody
asked. That is not laziness about correctness. It is the correct amount of
work.

## 7.6 Three ways to see `≡`

**As an evaluator with a stopwatch.** Run both sides a bit, and compare. The
only question is how much work to do before you give up, and
[Part VI of the guide](../README.md) is ten chapters about that question.

**As a rewriting game.** Seven moves are legal. Two terms are the same when
some sequence of legal moves joins them. The kernel searches for that sequence
in a fixed order, cheapest first.

**As a licence to run your program.** The kernel is allowed to execute your
code while it checks your proof. `rfl : 2 + 3 = 5` makes it add. A proof about
a sorting function may make it sort. This is the one place where a proof
checker is also an interpreter.

---

## 7.7 Why the order of the questions matters

The seven rules are not tried in any order. A real kernel asks the cheap
questions first, and the order is close to this.

1. Are the two terms the **same data** already? Compare, and stop.
2. Reduce both a little, but **do not** unfold a definition yet.
3. Is either side a proof? Then proof irrelevance settles it.
4. Now unfold definitions, one side at a time, and compare again.
5. Only then compare an application against an application, argument by
   argument.

Each step is cheaper than the next. Lean's kernel uses this order, and our
checker had to learn it. Two chapters of the implementation part,
[compare before you unfold](../19-compare-before-you-unfold.md) and
[ask the cheapest question first](../20-ask-the-cheapest-question.md), are that
lesson with the measurements attached.

---

### If you write TypeScript

**Your compiler already reduces types, and it already runs out of fuel.** This
is real TypeScript, and the error after it is real output from `tsc`:

```ts
type Tuple<N extends number, A extends unknown[] = []> =
  A["length"] extends N ? A : Tuple<N, [...A, unknown]>
type Add<A extends number, B extends number> =
  [...Tuple<A>, ...Tuple<B>]["length"]

type Fine = Add<2, 4>        // 6
type TooFar = Add<5000, 5000>
```

```text
error TS2589: Type instantiation is excessively deep and possibly infinite.
```

Read `Add` once more. That is **addition, in the type system**, written with
recursion and pattern matching. It is section 7.2 with different names, and
`TS2589` is a work budget, hit.

The difference is what happens when the budget runs out. `tsc` gives up on a
**type** and the rest of your file still compiles. Our checker gives up on a
**declaration** and says so, and later chapters measure that in seconds.

**You have met "stuck" too.** Section 7.4 already showed it: `IsString<T>`
waits while `T` is open, and `0 + n` waits while `n` is a variable. Same
behaviour, two compilers.

**`rfl` is a type-level test you have written before.** A test with
`expectTypeOf` from Vitest, or with `tsd`, asserts that two types are the same
and lets the compiler decide. `rfl : a = b` is that assertion, and here the
decision may involve running your program.

| | reduces types | gives up at a limit | compares by |
|---|---|---|---|
| TypeScript | conditional, mapped and template literal types | `TS2589` | structure, after reduction |
| Lean | β δ ι ζ η, and the two extra rules | `REAN_FUEL` here, and a recursion guard in Lean | [alpha equivalence](../GLOSSARY.md#alpha-equivalence), after reduction |

One honest difference, in Lean's favour and against it at once. `tsc` reduces a
small type language with no values in it. Lean reduces **your program**, and a
program can do anything. That is why chapter 7 is the hardest chapter and why
ten chapters of this book are about what it costs.

## 7.9 Check yourself

1. Why does a proof checker need an evaluator inside it?
2. `rfl` proves `n + 0 = n` and not `0 + n = n`. Why?
3. What do the two words in "weak head normal form" each rule out?

### Answers

1. Because of the conversion rule. A term keeps its type under computation, so
   to compare two types the checker may have to compute.
2. `Nat.add` recurses on its second argument. `n + 0` has a constructor there,
   so ι fires. `0 + n` has a variable there, so the term is stuck.
3. **Weak** rules out reduction inside a binder. **Head** rules out reduction of
   the arguments. Only the outermost shape is made stable.
